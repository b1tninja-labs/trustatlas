# What trustatlas can say, and what it cannot yet say

This is the roadmap for the supply chain of trust anchors: every obligation the site could plausibly take
on, with an honest status against the tree at `HEAD`. The north star is the question "which certificates has
some globally trusted program issued, and how do we know?" — and a row that overstates coverage turns that
into marketing.

**The honesty rule:** a row may read `[ok]` only when a named test would fail if the behaviour regressed.
`trustatlas` has no test suite, so **no row here reads `[ok]`**, and none may be promoted until a test
exists to defend it. Landed tools therefore read `[part]`: the code runs and its artifact is the evidence,
but nothing re-checks the claim when the tool changes.

Legend: `[ok]` implemented and pinned by a named test -- `[part]` partial, with what is missing stated --
`[ ]` not implemented -- `[no]` deliberate non-goal.

Update the affected row in the same commit that changes the behaviour. `AGENTS.md` governs what may be added
here; `PLAN.md`'s gating rule and its **Unverified** section bind this document and are not summarised away.

| `ta.readers_via_command` | PLAN.md P2 | `[part]` | **Node and Python were read on 2026-11-07 through one new seam rather than two new tools**: `collect_bundle.py --reader <exe> --reader-arg …` asks an executable to print PEM on stdout and feeds it to the same `index_pem` as every other store, argv passed directly with no shell. Node v25.9.0 compiles **145** anchors into its binary and **certifi's 120 are a strict subset of them** — the second subset relation recorded in this project, the first being curl inside the unfiltered NSS built-ins — while NSS-as-TLS (117) shares 114, leaving 31 anchors Node still carries that Mozilla no longer trusts for TLS: Node's set is a vintage, not a current list. `python.schannel` is the day's sharpest result: `ssl.create_default_context()` loads **72** anchors where PowerShell's provider lists **68** in the same hive, 54 shared. The 14 Python omits are code-signing and time-stamping roots; the 18 it adds are not anchors by any reading (`RapidSSL TLS RSA CA G1`, `GoDaddy TLS Intermediate CA DV - R1v1`, `Microsoft Update Secure Server CA 2.1`, `Microsoft Secure Server CA 2011`, `Microsoft Code Signing PCA 2024`, a Microsoft TLS OCSP responder). Mechanism unresolved at commit time — the third reader, `certutil -store Root`, is one command and was run next; the consequence is not, since a client that loads an issuing CA as a trust anchor terminates chains there. That mechanism was measured the same day, one command after the commit that left it open, and it is a store graph rather than a broken client: ROOT physically holds 16 certificates (`certutil -store Root` reports exactly those 16), AuthRoot holds 52, CA holds 7, and PowerShell's listing of 68 is precisely ROOT union AuthRoot, verified by thumbprint containment with none of the 7 CA entries appearing. `HKCU\SOFTWARE\Microsoft\SystemCertificates\ROOT\Certificates` is empty, so the user-hive mirror was the provider following links, and the nothing-user-installed negative now rests on 0 physical entries. crypt32 under a purpose filter drops the signing-only entries and admits linked contents instead; 11 of the 18 remain unattributed, pending an enumeration of the store's link list rather than another guess. **Closed later the same day, by the tools rather than by ad-hoc scripting:** `collect_store.py` gained `CA` as a collectable store (deliberately not in the default set, because adding it would change what the machine artifact claims and every join computed from it), and `Cert:\CurrentUser\CA` holds **23** entries of which **exactly 18** are in Python's set. ## 4. Deliberate non-goals

| Obligation | Spec | Status | Where | Milestone |

| `ta.protocol_logic` | PKI parsing | `[no]` | `AGENTS.md`: parsing anchors is `asn1core`, path and issuer links `pkix`, CT `ctspy`, storage and coverage `certledger`, DANE and DNSSEC `namespy`. A second, laxer PKI here is the one thing a trust map cannot survive | - |

## 5. Board projection

`py sdk-forge/sync_roadmap.py --project trustatlas --check` projects this matrix onto GitHub issues; the
issues are collected on Project V2 **#4 "Protocol SDK portfolio"**, the only board. Read with
`gh project item-list 4` on 2026-11-07: **20 items** from this repository, all in Backlog — 9 `status:partial`,
7 `status:unimplemented`, 4 `type:non-goal`, one per row of sections 1 to 4. The whole board held 102 items
across five repositories (`sdk-forge` 50, `trustatlas` 20, `pkix` 19, `ctspy` 7, `certledger` 6).

This section is a dated snapshot, not a live count. The board is the live view; neither is the source of
truth. **This file is**, and a board cannot enforce a rule — only a test can.

The `Milestone` column places each row on `PLAN.md`'s P0-P7 phasing. A `Test:` id marked `(to be written)`
names the test that would let the row move past `[part]`; no such file exists, because `trustatlas` has no
test suite yet.

## 6. Open questions

- **Cross-sign reach has no row.** `PLAN.md` P6 and its design goal (formerly `ta.reach`: reach computed via
  `pkix`, not by hand) are not carried by any row above. Whether that is a new row or part of
  `ta.render_blocklist` is undecided, so no row was invented.
- **`ta.collect_ctl` has no phase.** It fetches the Microsoft program that P2 is about, but decoding it waits on
  `pkix` M7 (`ta.ctl_decode`); P2 is the likely placement and is not asserted here.

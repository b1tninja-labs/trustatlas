# What trustatlas can say, and what it cannot yet say

This is the roadmap for the supply chain of trust anchors: every obligation the site could plausibly take
on, with an honest status against the tree at `HEAD`. The north star is the question "which certificates has
some globally trusted program issued, and how do we know?" — and a row that overstates coverage turns that
into marketing.

**The honesty rule:** a row may read `[ok]` only when a named test would fail if the behaviour regressed.

**Where this stands, measured 2026-11-14 (Python 3.14.3, `PYTHONDONTWRITEBYTECODE=1 python -m pytest -q -p no:cacheprovider`):**
`tests/` holds thirteen files; **111 pass, 0 fail, 1 strict xfail** (a `collect_certdata` defect pinned, not fixed:
row `ta.collect_certdata`), and `ruff check tools tests`,
`ruff format --check tools tests` and `mypy` are all clean (row `ta.suite_green`). `.probe_spki/` is the one
untracked path left (owner decision 1).
**No row reads `[ok]`**: rows whose named test now passes read `[part]` until `projecthub`'s evidence check has run
against a commit, because a passing test is not yet proof that it would fail on regression. `tests/test_roadmap_rows.py`
(row `ta.roadmap_gate`) now checks that every `[ok]` row's test exists, that every `Test:` id not marked
`(to be written)` exists, and that a marked one does not.

The shape, so no one reads this as a package: nine tracked scripts under `tools/` plus one untracked
(`check_spki_artifact.py`), stdlib only, writing artifacts to `--data`. `ta.package` is `[no]` and
`tests/test_pyproject.py` pins the refusal.

Legend: `[ok]` implemented and pinned by a named test -- `[part]` partial, with what is missing stated --
`[ ]` not implemented -- `[no]` deliberate non-goal.

Update the affected row in the same commit that changes the behaviour. `AGENTS.md` governs what may be added
here; `PLAN.md`'s gating rule and its **Unverified** section bind this document and are not summarised away.

## 2a. Host joins for pkgtrust (added 2026-11-13)

pkgtrust wants, per distribution hostname, the chain the host presents and which root programs list a key in it.
`PORTFOLIO.md` section 9 item 15 settles the split: **TLS chain capture lives in `certledger`'s transport layer; trustatlas
only joins captured chains against trust stores and never connects to a host.** So there is no `collect_chain.py` here (the
2026-11-13 review proposed one; that row is withdrawn), and the scripts below read files. The word "trusted" does not
appear in any output: a join says only that a presented certificate's key (SPKI SHA-256) equals a key some program lists.
Path validation, "chains to" and "is trusted for TLS in P" are `pkix`'s, and stay `[ ]` here until it exists.
